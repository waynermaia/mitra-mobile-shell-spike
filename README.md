# mitra-mobile-shell-spike

Spike (2026-11-05): wrap an app published by Infusion in a Capacitor shell and take it to
internal testing (Google Play) and TestFlight (Apple). Companion note:
`vault/20-projects/superficie-apps-stores/spike-apps-nas-stores-2026-11-05.md`.

Target app: **Bolo Mobile Spike**, created in Infusion for this test. Published URL (https://a1-a17htrxztqy0pw4apmihj62ou.infusion-ai.cloud) lives in
`capacitor.config.json` (`server.url`).

## What is here

- `capacitor.config.json`: app id `cloud.infusion.bolomobilespike`, WebView loading the
  published app. Spike only: production must bundle the web assets into `www/`.
- `www/index.html`: offline fallback page (bundled assets, not used while `server.url` is set).
- `assets/`: logo as SVG; `npm run assets` regenerates every icon and splash for both platforms.
- `android/`, `ios/`: native projects generated by `cap add`. iOS uses Swift Package Manager,
  so no CocoaPods on the build machine.
- `.github/workflows/mobile.yml`: three jobs.
  - `android`: signed release AAB and APK as artifact (unsigned when secrets are missing).
  - `ios-simulator`: compile check, no signing.
  - `ios-testflight`: manual run with `upload_testflight=true`; archives with cloud signing
    through an App Store Connect API key and uploads to TestFlight.

Plugins installed: app, splash-screen, status-bar, share, haptics, network, browser,
push-notifications (push needs Firebase on Android and the aps entitlement on iOS; not wired).

## Generator (POC, 2026-11-08): one shell per app, from the platform app id

`generator/generate.mjs` turns this repo into a template. Input is the platform app UUID (or a
published URL, or a small descriptor in `apps/*.json`); output is a complete Capacitor project
under `out/<slug>/` (git-ignored) with every patch the spike proved already applied.

```bash
node generator/generate.mjs --app f98fa7c6-00f3-433a-9646-66e3d497995f --build debug --install
node generator/generate.mjs --descriptor apps/bolo.json --build debug
node generator/generate.mjs --url <url> --name "Nome" --app-id br.com.x.app --icon logo.svg \
  --theme "#112233" --version 1.2 --build-number 7 --associated-domains --no-ios
```

Source of truth is the platform: `GET {api}/code-studio/api/v1/apps/{app}/info` (public route,
no token; `--api` defaults to `https://beta.mitralab.io`) gives the name, the served origins
(platform host first, active custom domain last; the generator loads the last one), the accent
color and the login logo. The page is only scraped for what the API does not carry yet: the
icon when the app has no login logo (`apple-touch-icon`, then `rel=icon`; SVG or PNG, inline
`data:` works), plus title and `theme-color` in `--url` mode.
Derived: slug, app id `cloud.<brand>.<slug>`, host for the App Link. Steps: write
`package.json` (same pinned deps and lockfile as this repo), `capacitor.config.json`,
`www/index.html` offline page, `assets/logo.*`; `npm ci`; `cap add android` and `cap add ios`;
patch Android (App Link intent-filter for the host, `MainActivity.onNewIntent`, release signing
from env, `local.properties`), patch iOS (`ITSAppUsesNonExemptEncryption`, version and build
number, optional `App.entitlements` with `applinks:<host>` wired through
`CODE_SIGN_ENTITLEMENTS`); `capacitor-assets generate`; `cap sync`; copy
`.github/workflows/mobile.yml` and write a README plus `mitra-shell.json` (the descriptor echo).
`--build debug|release` runs Gradle, `--install` does `adb install -r`. The run ends with
`out/last.json` and, under GitHub Actions, the same fields in `GITHUB_OUTPUT`.

CI per app: `.github/workflows/shell.yml` (Actions -> App shell -> Run workflow) takes the app
UUID (or a URL), the API base, an optional bundle id override, the marketing version, an optional
build number, and the switches `associated_domains` (default on), `upload_testflight`,
`upload_play`, plus the TestFlight group and the Play track. Both jobs first resolve the identity
(`generate.mjs --identity`) and the build number (`asc.mjs next-build`: App Store Connect latest
build + 1, so iOS and Android move together; the run number when the app has no record yet or
`build_number` is given). The Android job builds the signed AAB and APK (artifact
`android-<slug>`) and, when the `PLAY_SERVICE_ACCOUNT_JSON_B64` secret exists, uploads the AAB
to the Play track with `play.mjs upload` (exit 3 = the app or its first AAB are missing in Play
Console, reported as a warning). The iOS job does an unsigned device build by default and, with
`upload_testflight`, registers the bundle id when missing (`asc.mjs ensure-bundle-id`), checks
the app record (`asc.mjs app-id`, exit 3 with the manual step when missing), archives with
cloud signing, uploads, waits for processing and adds the build to the TestFlight group
(`asc.mjs wait-build` and `add-to-group`, group created when missing). Runners come from the
repository variables `LINUX_RUNNER` and `MACOS_RUNNER` (defaults `ubuntu-latest` and
`macos-26`), so moving to self-hosted machines is a variable change.

### iOS sign-in inside the shell (2026-11-09)

`generator/templates/ios/SceneDelegate.swift` replaces the Capacitor one in every generated
project. It does two things the published app cannot: a top-level navigation to an identity
host (the platform API host, `accounts.google.com`, Microsoft, Apple; list in
`capacitor.config.json` under `plugins.MitraShell.authHosts`, `--auth-hosts` adds more) opens in
an `ASWebAuthenticationSession` whose callback is the app's own host (iOS 17.4+ `https`
callback), and the URL the session returns, or a Universal Link, is loaded in the WebView with
a fresh `shellLink` query value so the SDK completes the sign-in at boot, the same move as
`MainActivity.onNewIntent` on Android. Safari alone would not do it: it does not turn the SDK's
JavaScript redirect into a Universal Link. The `https` callback needs `webcredentials:<host>`
next to `applinks:<host>` in `App.entitlements` (both written by `--associated-domains`) and the
host serving the AASA file. Below 17.4, or when the session cannot start, the behavior is the
old one (system browser).

### Association files the host must serve

`generator/wellknown.mjs --project out/<slug> --team <Apple Team ID> --keystore ... --play-sha256 ...`
writes `out/<slug>/wellknown/apple-app-site-association`, `assetlinks.json` and the
KeyValueStore value the platform edge serves them from (key `mobile:<host>`; the platform change
is `mitra-terraform` module `storage`, function `apps-wellknown.js` on a `/.well-known/*`
behavior), and prints the `aws cloudfront-keyvaluestore put-key` command for the operator. The
Android fingerprints are the upload key (APK by adb) and the Play App Signing key (store
installs); both are listed for Bolo.

Still manual, by design of the stores: the app record in App Store Connect (no public create-app
endpoint), the app and its first AAB in Play Console, and the Play service account key
(credential creation). Everything after those is the workflow.

npm run assets          # regenerates icons and splash from assets/*.svg
npx cap open ios        # needs Xcode (not installed on this Mac)

export `ANDROID_KEYSTORE_PATH=.secrets/upload-spike.jks`, then `cd android && ./gradlew bundleRelease`.

## Morning checklist: what only the account owner can do

### Google Play (internal testing): DONE on 2026-11-05

Done through the organization account that already existed (it also hosts the Mitra and
Infusion apps): app "Bolo Mobile Spike" created, the `android-release` AAB of run 42059892570
published to the internal testing track, tester list created and opt-in link generated
(`https://play.google.com/apps/internaltest/4699351945255650955`). Play App Signing was on by
default, so the installed APK is signed by Google: production `assetlinks.json` must carry the
Google signing certificate fingerprint shown under App signing in the console, not the upload
key fingerprint (the upload key only matches APKs installed with `adb`). The steps below stay
as the recipe for the next app.

1. Have a Play Console developer account (USD 25 once). Organization accounts need a D-U-N-S
   number; personal accounts created after 2023-11-13 must run a closed test with 12 testers
   for 14 days before production (internal testing is not blocked by that).
2. Play Console: Create app -> name "Bolo Mobile Spike", app, free. Fill the mandatory
   declarations (privacy policy URL, data safety, content rating, target audience).
3. Download the `android-release` artifact of the last green run and upload the `.aab` to
   **Testing -> Internal testing** by hand. The first upload of every app must be manual; the
   Play Developer API only works after that.
4. Add testers (e-mail list) and share the opt-in link.
5. Later, for automation: Play Console -> Setup -> API access -> service account; store the
   JSON as a secret and add an `upload-play` job (Gradle Play Publisher or `r0adkll/upload-google-play`).

The upload keystore for this spike is in `.secrets/upload-spike.jks` (git-ignored) and in the
repo secrets `ANDROID_KEYSTORE_B64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`. Play App
Signing lets Google hold the final key, so this upload key can be reset later.

### Apple (TestFlight): DONE on 2026-11-05

Build 1.0 (run 42092822789) uploaded to App Store Connect for the app record created that
day (id 6831288469). Two things only the run could teach:

- An API key with the **App Manager** role archives fine but `-exportArchive` fails with
  "Cloud signing permission error" / "No signing certificate iOS Distribution found": only
  an **Admin** key may create the cloud-managed distribution certificate, and there is no UI
  option to grant that to an App Manager key. The alternative for a platform that must not
  ask customers for an Admin key is to create the distribution certificate (CSR) and the
  profile through the API and sign with them instead of cloud signing.
- App Store Connect rejects builds made with the iOS 18 SDK ("All iOS and iPadOS apps must
  be built with the iOS 26 SDK or later"). GitHub `macos-15` runners default to Xcode 16.4;
  `macos-26` defaults to Xcode 26.6 and worked.

- After processing, TestFlight asked the "App Encryption Documentation" question before the
  build could be tested. For a shell that only uses HTTPS from the OS the answer is "None of
  the algorithms mentioned above"; `ITSAppUsesNonExemptEncryption = false` in `Info.plist`
  (added after build 10) answers it at upload time, so the pipeline never needs a human there.

The steps below stay as the recipe for the next app.

1. Apple Developer Program membership (USD 99/year) on the account that owns the app. For a
   company, enrollment needs a D-U-N-S number and can take days.
2. App Store Connect -> Users and Access -> Integrations -> App Store Connect API -> generate a
   **Team** key with role **Admin** (App Manager is not enough for cloud signing, see above).
   Note the Key ID and the Issuer ID and download the `.p8` once (it cannot be downloaded again).
3. App Store Connect -> Apps -> `+` -> New App: platform iOS, name "Bolo Mobile Spike", bundle
   ID `cloud.infusion.bolomobilespike` (register it under Certificates, Identifiers and
   Profiles if it is not listed), SKU `bolo-mobile-spike`. Creating the app record is not
   covered by the API as far as this spike could confirm.
4. Repo secrets: `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8_B64` (`base64 -i AuthKey_XXXX.p8`)
   and `APPLE_TEAM_ID` (Membership details).
5. Actions -> Mobile shell -> Run workflow with `upload_testflight` checked. The job archives
   with `-allowProvisioningUpdates` (creates certificate and profile on the account) and
   uploads. The build appears in TestFlight after Apple's processing (minutes); add internal
   testers there.
6. Before a real App Store submission: Sign in with Apple if the app offers Google login,
   privacy policy URL, and native features beyond the WebView (guideline 4.2).

## Social sign-in inside the shell (proved on the emulator, 2026-11-05)

A plain WebView cannot finish Google sign-in: Capacitor sends any host outside `server.url`
to the system browser, and in popup mode the web app waits for a popup answer that never
arrives. What works, end to end on a Pixel 7 emulator (API 35):

1. The web app calls `signInWithGoogle({ mode: 'redirect' })` when `window.Capacitor` exists
   (the Bolo app does this since its second publish). The SDK stores the CSRF context in the
   WebView's `sessionStorage` and navigates to the auth page; Capacitor opens that in Chrome.
2. Chrome runs the auth page and Google, then the auth page redirects to the app origin with
   `#codeMitra=...&stateMitra=...`.
3. The manifest declares an App Link (`autoVerify`) for the app host, so Android hands that
   URL to the shell instead of Chrome. `MainActivity.onNewIntent` loads it in the WebView
   with a fresh `shellLink` query value, which forces a full document load.
4. The app boots, `completeGoogleSignInRedirect()` finds the fragment and the context,
   exchanges the code at IAM, and the user is signed in.

On the emulator the domain was approved by hand:

```bash
adb shell pm set-app-links --package cloud.infusion.bolomobilespike 2 <app host>
adb shell pm set-app-links-user-selection --user 0 --package cloud.infusion.bolomobilespike true <app host>
```

Production needs the platform to serve `https://<app host>/.well-known/assetlinks.json`
(package name + upload certificate SHA-256) and, for iOS, `apple-app-site-association`.

WebView inspection: `webContentsDebuggingEnabled` is on in `capacitor.config.json`;
`adb forward tcp:9333 localabstract:webview_devtools_remote_<pid>` exposes the DevTools
protocol on `http://localhost:9333/json`.

Emulator setup used here (no Android Studio): `sdkmanager emulator
"system-images;android-35;google_apis;arm64-v8a"`, `avdmanager create avd -n spike35 -k ... -d pixel_7`,
then `hw.keyboard=yes` in `~/.android/avd/spike35.avd/config.ini` so the Mac keyboard works.

## Findings to carry into the Proposal

- Both stores require the content owner's own account; the platform can automate everything
  after an API key (Apple) and a service account (Google) are handed over.
- The two manual steps that remain are "create the app record" (Apple) and "first upload"
  (Google).
- iOS builds need macOS; GitHub Actions `macos-26` worked for this spike without any local
  Xcode.
